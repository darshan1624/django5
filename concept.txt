Permission Tables: 
 Whenever we do makemigrations, migrate for first time following 
 tables are created
- content_type
- auth_permission
- auth_user_user_permissions
- auth_group_permissions
- auth_user_groups

- content_type 
 It stores a app-model mapping for every installed app.
 e.g.: suppose app "store" has "Product" model.
	id	app_label	 model
	5 	store   	Product  

- auth_permission
 whenever a model is created and makemigrations, migrate is done.
 4 permissions are created for each new model. 
	e.g.: model product
	app_name.add_product, . change_product, 
	.delete_product, .view_product 
 These permissions are linked to models defined in content_type using
 forign key content_type_id. 
 e.g.:
	id 	content_type_id    codename 		name
	20	5		   add_product      Can add Product		
	21	5		   change_product      Can change Product
	22	5		   delete_product      Can delete Product
	23	5		   view_product      Can view Product		    

- auth_user_user_permissions
	These permissions are assigned manually.
	columns : (id user_id permission_id)

- auth_group 
	columns : (id name)

- auth_user_groups
	columns : (id user_id group_id)



Django's built-in authentication and permission system uses the 
following methods on the user model
- has_perm(perm, obj=None)
- has_perms(perm_list, obj=None)
- has_module_perms(app_label)

	def has_perm(self, perm, obj=None):
		return self.is_superuser

	def has_module_perms(self, app_label):
		return self.is_superuser
# gives permission only if the user is_superuser

They are used in Django admin, views, templates	to check if the user

def assign_permission(user, role):
    role_permission = PERMISSION_CONFIG.get(role)
    for model, permissions in role_permission.items():
	content_type = ContentType.objects.get(
			app_label = model._meta.app_label,
			model = model._meta.model_name
			)
	for perm_codename in permissions:
	    Permission.objects.get(
		content_type = content_type,
		codename = f'{perm_codename}_{model._meta.model_name}'
		)
	    user.user_permissions.add(permission)

Cookies: 
cookies are key value pairs sent by server to store on client machine.
They are common way for client side storage.

Reasons to use cookies:
- Http requests are stateless. They doesnot remember anything between
 the two requests. 
- Cookies allows the client to send some data with every request. 
 e.g. It can store tokens in JWT or session ids in session auth.
- Non sensitive data can be stored like Theme(light/dark mode), 
 language.

Syntax to set cookie
	HttpResponse.set_cookie(key, value='', max_age=None, 
		expires=None, secure=True, httponly=True)

	max_age - In secs (after this token gets expires)
	expires - In datetime format
	secure - cookie can only be set or get when request are https
		and not http (on devlopement server keep False if 
		using http)
	httponly - cant access cookie on frontend only accesible on
		server, prevents XSS(cross site scripting)

Abstarct Model
When we have common fields in two or more models we can can 
include common filelds in single Base model.
Then inherit the Base model in other models.
- abstract = True
- No db table will be created for abstarct model
- child class will inherit abstract class fields and methods 
- Not possible to intilaize values directly

Suppose we have to create three models.
Student(name,age,fees)
Teacher(name,age,salary,join_date)
Constructor(name,age,payment,join_date)

# We can name,age,join_date is repeated in two or more models.
# Such common fields can be avoided by using Abstract Base Model.

How to create Abstract Base Model?
from django.db import models

class AbstractBaseModel(models.Model):
    name = models.CharField(max_length=255)
    age = models.IntegerField()
    join_date = models.DateField()

    class Meta:
	abstract = True

class Student(AbstractBaseModel):
    fees = models.IntegerField()
    join_date = None  #Fields not required can be set to None

class Teacher(AbstarctBaseModel):
    salary = models.IntegerField()
    
class Constructor(AbstarctBaseModel):
    payment = models.IntegerField()
    join_date = models.DateTimeField #if required custom or
				     diff override the filed



Multi Table Inheritance
When you want Base model table to be create with along with child
class model. 
There is one to one relationship between base model and child
class. 
Any entry deleted from child class will get deleted from 
ExamCenter as well but not vice versa. 
If tried to delete from Base Model and relation ship exist in
child class it will throw error.

Suppose you have to create two models with common fields.
ExamCenter(center_name, center_city)
Student(name, roll, center_name, center_city)

How to create Muti Table Inheritance?
class ExamCenter(models.Model):
    center_name = models.CharField(max_length=255)
    center_city = models.CharField(max_length=255)

class Student(ExamCenter):
    name = models.CharField(max_length=255)
    roll = models.IntegerField()

- Both models ExamCenter, Student will be created. Student will 
have ExamCenter fields as well.


Proxy Model:
When you want to change the behaviour of the existing model, then
we use the proxy model.
With proxy model we have two models, but table in db remains only
one which is original.
In proxy model you cannot create new field.

How to create Proxy model?
class Product(models.Model):	
    name = models.CharField(max_length=100)
    price = models.IntegerField()
    stock = models.IntegerField()

class ProxyProduct(Product):
    class Meta:
	proxy = True 


Why to use proxy model?
- Add helper methods

Model manger:
Model Manager acts as a interface bwteeen model and orm query. 
Every model has on default manager inbuilt.
By default its 
	objects = models.Manager()
# That is how we can access Student.objects.all().
# Student table has objects property(attribute).

Why to create custom Model manager? 
- Modify queryset result
- Add extra custom manager method

How to create custom Model Manager?
from django.db import models

class CustomStudentManager(models.Manager):
    def get_queryset(self):
	# By default manager order_by id but now it will be name
	return super().get_queryset().order_by('name')
	

class Student(models.Model):
    name = models.CharField(max_length=255)
    age = models.IntegerField()
    join_date = models.DateField()
    fees = models.IntegerField()

    # objects = models.Manager() #By default inbuilt manager 
    objects = CustomStudentManager()

# modified .get_queryset()


How to create custom manager Method?
class CustomStudentManager(models.Manager):
    def get_stu_roll_range(self, r1, r2):
	return super().get_queryset().filter(roll__range=(r1,r2))

Helper method vs Custom Manager Method?
- Helper methods are used when you have model object already.
- unlike Model Manager Method were you get entire query.
- Use helper methods to add logic for a single instance
- Use manager methods to filter/query sets of objects from the DB
